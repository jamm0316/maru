# 읽기 화면 작업 문서

상태: 1부(6단계) 구현 완료. 설치된 앱도 1부 빌드다. 2부(화면 블록, 기본 배치, 첫 메시지)는 구현을 마쳤고 설치된 앱에는 아직 반영하지 않았다. 2부의 규격은 11절과 12절, 구현하면서 달라진 것은 13절에 있다. 구현하면서 계획과 달라진 것은 맨 아래 10절에 적었다. 이 문서의 4.1절과 4.4절은 계획 당시의 내용이고, 10절이 실제 구현이다.

## 1. 무엇을 만드는가

터미널(Claude Code 세션)은 그대로 두고, "읽기 화면"을 켤 수 있게 한다.

- 읽기 화면을 켜면 가운데에 큰 읽기 영역이 생긴다. 내 질문과 에이전트의 답변을 제목, 목록, 표, 코드로 그려서 보여 준다.
- 읽기 영역 아래에 입력창이 있다. 여기에 쓴 문장은 앱이 터미널에 대신 넣는다.
- 터미널은 오른쪽으로 옮겨 좁게 보이고, 접을 수 있다.
- 읽기 화면을 끄면 지금 화면 그대로다.

## 2. 결정

| 번호 | 쟁점 | 결정 | 근거 |
|---|---|---|---|
| D1 | 배치 | 읽기 영역은 가운데, 터미널은 오른쪽. 읽기 화면을 켠 동안 오른쪽 카드 열(스쿼드, 할 일)은 접는다 | 사용자 결정. 기본 창에서 가운데 폭 816px에 둘을 넣으면 둘 다 좁다 |
| D2 | 데이터 경로 | 훅 두 개가 질문과 최종 답변을 세션별 기록 파일에 덧붙인다. 앱은 그 파일만 읽는다 | 권한 확인이 뜨지 않는다. 대화 기록 파일의 내부 형식에 기대지 않는다 |
| D3 | 그릴 내용 | 답변의 마크다운을 그대로 그린다 | 평소 답변의 표가 그대로 표로 보인다. 지시문과 추가 토큰이 필요 없다 |
| D4 | 화면 블록(`maru-surface`) | 첫 판에서 뺀다. 2부로 미룬다 | D3으로 표와 목록이 이미 그려진다. 블록은 마크다운으로 안 되는 카드(막대 등)가 필요해질 때 넣는다 |
| D5 | 입력창 | 세션이 쉬고 있을 때만 보낸다. 권한 확인과 선택지는 터미널에서 한다 | 앱이 권한 확인 창에 대신 답하면 안 된다 |
| D6 | 링크, 이미지, 버튼 | 그리지 않는다. 링크는 글자로만 보인다 | 외부 글이 섞인 답변이 누를 것을 만들지 못하게 한다 |
| D7 | 답이 뜨는 시점 | 턴이 끝난 뒤 한 번 | 확인된 경로는 최종 답변만 준다. 진행 상황은 터미널에서 본다 |
| D8 | 다음 묶음과의 관계 | 학습 상태 카드 등은 앱이 직접 만든다. 그리는 함수는 같이 쓴다 | 이 기능이 실패해도 다음 묶음은 영향이 없다 |
| D9 | 기록 | 날짜별 횟수만 센다 | 내용은 통계에 쓰지 않는다 |

1차 문서에서 바뀐 것은 이렇다.

- 아래 도크를 버리고 좌우 배치로 바꿨다.
- 큰 읽기 영역이 비지 않도록 답변 전체를 그린다. 그래서 마크다운 해석, 질문·답변 기록, 입력창이 범위에 들어왔다.
- 답변 전체를 그리면 화면 블록 없이도 표가 보인다. 블록과 지시문은 2부로 미뤘다. 터미널에 같은 표가 두 번 보이는 문제도 없어진다.

## 3. 직접 확인한 것

| 확인한 것 | 결과 |
|---|---|
| Stop 훅 입력에 최종 답변 글이 있는가 | 있다(`last_assistant_message`). 화면 없는 방식으로 한 번 확인했다 |
| 훅이 파일을 쓸 때 권한 확인이 뜨는가 | 뜨지 않았다 |
| 훅 항목의 제한 시간이 듣는가 | 듣는다 |
| 앱이 권한 대기 상태를 아는가 | 안다. 기존 원격 입력 검사(`rcCanSend`)가 작업 중과 권한 대기 중에 입력을 거부한다 |

확인하지 못한 것은 이렇다. 표의 단계에서 확인한다.

| 미확인 | 확인할 단계 |
|---|---|
| 대화형 세션의 Stop 훅도 같은 필드를 주는가 | 2단계 |
| 질문을 받는 훅(UserPromptSubmit) 입력에 질문 글이 들어 있는가 | 2단계 |
| 터미널 폭을 320px까지 줄여도 권한 확인 창을 읽을 수 있는가 | 4단계 |
| 붙여넣기 방식으로 넣은 슬래시 명령이 명령으로 인식되는가 | 5단계 |
| 도구 호출 사이의 중간 글 | 받지 못하는 것으로 보인다. 첫 판은 최종 답변만 그린다 |

## 4. 규격

### 4.1 기록 파일

- 경로: `data/state/app/<세션 식별값>.talk.jsonl`
- 한 줄: `{"v":1,"at":<초>,"role":"user"|"assistant","text":"<글>"}`
- 쓰는 곳: 새 스크립트 `scripts/talk-log.sh`. 질문 훅과 Stop 훅에서 불린다.
- 제한: 글 하나 64KB(넘으면 자르고 잘렸다고 표시), 파일은 최근 200줄만 남긴다.
- 작업 공간을 닫으면 앱이 이 파일을 지운다.
- 끄는 방법: `MARU_NO_TALK_LOG=1`이면 훅을 붙이지 않는다. 그러면 읽기 화면에는 안내만 보인다.

### 4.2 마크다운 해석

순수 함수 `mdParse(text)`가 글을 아래 블록 목록으로 바꾼다.

| 블록 | 글에서의 모양 |
|---|---|
| 제목(1~3단계) | `#`, `##`, `###` |
| 문단 | 보통 글 |
| 목록 | `-`, `*`, `1.` 과 한 단계 들여쓰기 |
| 표 | `\|` 로 시작하는 이어진 줄. 구분 줄은 정렬 정보만 쓴다 |
| 코드 | 코드 펜스. 언어 이름은 꼬리표로만 보인다 |
| 인용 | `>` |
| 구분선 | `---` |

- 줄 안 꾸밈은 굵게(`**`)와 코드(`` ` ``)만 다룬다. 링크는 글자와 주소를 글로 보인다.
- 모르는 모양은 문단으로 그린다. 해석이 실패해 화면이 비는 일이 없어야 한다.
- 제한: 블록 400개, 표 12열 100행, 코드 블록 400줄. 넘는 부분은 자르고 "더 있음. 터미널에서 확인"이라고 보인다.

### 4.3 화면

| 항목 | 값 |
|---|---|
| 켜고 끄기 | 터미널 막대의 단추. 세션별로 기억한다. 기본은 꺼짐 |
| 읽기 영역 `.read-wrap` | 가운데. 질문은 오른쪽 말풍선, 답변은 본문 폭 최대 760px |
| 입력창 `.read-input` | 읽기 영역 아래에 고정. 여러 줄. Enter로 보내고 Shift+Enter로 줄을 바꾼다. 한글 조합 중의 Enter는 보내지 않는다 |
| 터미널 | 읽기 화면을 켜면 오른쪽 카드 열 자리로 간다. 폭은 기본 420px, 최소 320px, 최대 가운데 영역의 절반. 손잡이로 조절한다 |
| 터미널 접기 | 34px 띠로 접힌다. 띠를 누르면 펼친다 |
| 권한 대기 | 입력창을 잠그고 "터미널에서 답하세요"를 보인다. 터미널이 접혀 있으면 띠를 주황으로 바꾼다. 자동으로 펼치지는 않는다 |
| 작업 중 | 마지막 질문 아래에 "작업 중"을 보인다. 입력창은 잠근다 |
| 빈 화면 | 한 줄 안내 |
| 좁은 창(1100px 이하) | 읽기 영역만 보이고 터미널은 띠로 접힌다. 띠를 누르면 터미널이 읽기 영역을 덮는다 |
| 그리기 | `el()`의 textContent만 쓴다. 색은 style.css에 있는 변수만 쓴다 |

### 4.4 입력창이 보내는 방법

1. 렌더러가 글을 main에 넘긴다(IPC `read:send`).
2. main이 세션 상태를 직접 확인한다. 쉬는 중이 아니면 거부하고 이유를 돌려준다.
3. 제어 문자를 지운다. 길이는 16KB까지다.
4. 기존 붙여넣기 방식으로 터미널에 넣고 Enter를 보낸다.

- 렌더러의 판단을 믿지 않고 main이 다시 검사한다.
- 작업 중에 다음 말을 미리 넣어 두는 것은 첫 판에서는 터미널에서만 된다.

## 5. 안전

| 위험 | 대응 |
|---|---|
| 앱이 권한 확인 창에 글을 넣는다 | 쉬는 중일 때만 보낸다. main이 검사한다. 앱이 권한 대기를 아는 시점이 조금 늦을 수 있으므로 작업 중에도 막는다 |
| 답변에 섞인 외부 글이 화면을 속인다 | 글과 표만 그린다. 링크, 이미지, 버튼이 없다 |
| 기록 파일에 대화 내용이 남는다 | 이 컴퓨터의 `data/` 안에만 둔다. 최근 200줄만 남기고, 작업 공간을 닫으면 지운다. 끄는 변수가 있다 |
| 훅이 엉뚱한 곳에 쓴다 | 세션 식별값의 형식을 검사한다. 심볼릭 링크를 거부한다. 항상 0으로 끝난다 |
| 훅이 세션을 늦춘다 | 제한 시간 5초. 상태 훅과 다른 스크립트로 둔다 |
| 앱이 엉뚱한 파일을 읽는다 | 실제 경로가 `data/state/app` 안인지 확인한 뒤 읽는다 |

## 6. 구현 단계

| 단계 | 바꿀 파일 | 끝 조건 | 시험 |
|---|---|---|---|
| 1. 마크다운 해석 | `app/lib.js`, `app/test.js` | `mdParse`가 4.2대로 바꾼다. 제한을 지킨다 | 단위 시험: 제목, 겹친 목록, 표, 코드 펜스, 굵게와 코드, 닫히지 않은 펜스, 제한 초과 |
| 2. 기록 훅 | `scripts/talk-log.sh`(새 파일), `scripts/maru-claude.sh`, `.claude/settings.json`, `scripts/test-talk.sh`(새 파일) | 질문과 최종 답변이 4.1 형식으로 덧붙는다. 실패해도 0으로 끝난다 | 임시 폴더에서 가짜 훅 입력: 긴 글, 링크로 바꿔 둔 파일, 잘못된 세션 값, 200줄 넘김. 대화형 세션에서 두 훅의 입력을 한 번 확인한다 |
| 3. 읽기 | `app/main.js`, `app/preload.js`, `app/lib.js` | 세션별 기록을 읽어 렌더러에 준다. 수정 시각과 크기로 캐시한다. 개발용 가짜 대화 `MARU_APP_TALK=1` | 임시 data 복사본 |
| 4. 읽기 화면 | `app/renderer/index.html`, `style.css`, `renderer.js`, `app/i18n.js` | 4.3대로 보인다. 켜고 끌 때 터미널 글자 수가 다시 맞춰진다 | 가짜 대화로 1440x900과 900x560에서 화면을 찍어 직접 본다. 터미널 320px에서 권한 확인 창이 읽히는지 본다 |
| 5. 입력창 | `app/main.js`, `app/preload.js`, `renderer.js`, `app/lib.js` | 4.4대로 보낸다. 작업 중과 권한 대기 중에 거부한다 | 단위 시험(검사 함수). 임시 세션에서 보통 글, 여러 줄, 슬래시 명령, 한글 조합을 직접 본다 |
| 6. 기록과 문서 | `app/main.js`, `app/lib.js`, `docs/manual.ko.md` | 날짜별로 읽기 화면을 켠 횟수, 입력창으로 보낸 횟수, 터미널로 보낸 횟수를 센다 | 단위 시험 |

- 실제 `data/`는 시험에서 건드리지 않는다. 저장소를 임시 폴더에 복사해서 한다.
- `app/updater.test.js`는 돌리지 않는다.
- 단계마다 구현과 독립 검토를 따로 한다.
- 4단계부터는 앱을 다시 빌드해야 보인다. 설치된 앱의 교체는 사용자 승인 뒤에 한다.

## 7. 2부(이번에 하지 않는다)

- 화면 블록 `maru-surface`: 에이전트가 답변 끝에 카드, 막대 같은 화면을 쓰는 것. 1차 문서의 규격(마크다운 일부만 쓰는 블록, 출처 표지, 점선 테두리)을 그대로 쓴다. 앱 세션에 지시문 4줄을 붙여야 하므로 사용자 결정이 필요하다.
- 앱이 만드는 카드(학습 상태, 회고 영수증, "그동안" 브리핑)
- 도구 호출 사이의 중간 글
- 턴 도중에 답이 조금씩 그려지는 것
- 버튼으로 터미널에 입력 넣기, 차트, 이미지

## 8. 계속할지 판단하는 기준(제안값)

2주 써 본 뒤 본다.

| 판단 | 조건 |
|---|---|
| 계속한다 | 쓴 날의 절반 이상에서 읽기 화면을 켰고, 보낸 말의 절반 이상이 입력창에서 나갔다 |
| 그만둔다 | 읽기 화면을 켠 날이 2주에 3일 이하다 |

## 9. 사용자가 정할 것

1. 질문과 답변 글을 `data/state/app` 아래 파일에 남겨도 되는지(4.1).
2. 화면 블록을 2부로 미루는 것(D4).
3. 8절의 기준을 그대로 쓸지.

## 10. 구현하면서 달라진 것

| 항목 | 계획 | 실제 구현 | 이유 |
|---|---|---|---|
| 기록 파일 이름 | 앱이 터미널에 붙이는 세션 값 | Claude 세션 id(훅 입력의 `session_id`) | 앱의 값은 터미널을 띄울 때마다 바뀌어, 이어 연 세션에서 과거 대화가 사라졌다 |
| 오래된 기록 정리 | 작업 공간을 닫을 때만 | 닫을 때, 그리고 72시간 동안 바뀌지 않은 기록은 앱을 켤 때 | 세션이 바뀌어(`/clear` 등) 남은 파일을 치운다. 이어 열기 창(이틀)보다 길게 잡았다 |
| 기록 파일 크기 | 최근 200줄 | 최근 200줄이면서 6MB 이하. 아주 긴 글은 "기록하지 못함" 표지를 남긴다 | 긴 답변이 쌓이면 기록이 멈추는 문제가 있었다 |
| 화면 없는 실행 | 다루지 않음 | 앱 세션 안에서 돌린 화면 없는 실행은 기록하지 않는다 | 부모 세션의 기록에 섞였다 |
| 입력창이 보내는 조건 | 세션이 쉬는 중일 때 | 방금 답변이 정상으로 끝났고 그 뒤로 터미널에 입력이 없었을 때만 | 아래 "입력창의 판정" 참고 |
| 훅 | 질문 훅, 종료 훅에 기록 훅 추가 | 여기에 더해 도구 호출 직전(PreToolUse)에 상태를 "작업 중"으로 올린다 | 스스로 시작한 턴의 권한 확인 창을 가리기 위해서다 |
| 상세 화면 | 다루지 않음 | 프로젝트·기억 같은 상세 화면이 열린 동안에는 읽기 배치를 적용하지 않는다 | 상세 화면은 터미널 자리에 뜬다 |
| 대화 배치 | 답변 폭 760px | 질문과 답변을 폭 860px 기둥 안에 모은다 | 터미널을 접으면 질문과 답변이 멀어졌다 |

### 입력창의 판정

앱은 터미널 화면에 무엇이 떠 있는지 직접 알 수 없다. 처음에는 "쉬는 중이면 보낸다"로 만들었고, 독립 검토에서 권한 확인 창, 선택 메뉴, 다른 프로그램에 글과 Enter가 들어가는 길이 두 차례 발견됐다. 그래서 안전한 한 가지 경우만 허용하도록 바꿨다. 아래가 모두 참일 때만 보낸다.

- 터미널 앞에 있는 프로그램이 앱이 띄운 세션이다(앱이 기억한 프로세스 이름과 같다).
- 상태 파일의 원래 기록이 "쉬는 중"이다. 앱이 화면 표시용으로 낮춰 본 상태는 쓰지 않는다.
- 그 기록과 같은 때(앞뒤 15초)에 훅이 최종 답변을 기록했다. 실패로 끝난 턴에는 이 기록이 없다.
- 그 기록 2초 전부터 지금까지 터미널에 쓴 것이 없다. 사용자의 키 입력, 할 일 채우기, 입력창으로 보낸 것을 모두 센다. 터미널이 스스로 보내는 응답(포커스 알림 등)은 세지 않는다.
- 예외: 턴이 2초보다 짧으면 그 턴을 시작한 Enter가 위의 2초 창에 들어간다. 그래서 마지막 입력이 질문을 받은 그 초가 끝나기 전이고 답변 기록보다 앞이면 그 입력은 세지 않는다. 질문 기록은 이 터미널을 띄운 뒤의 것이어야 한다.
- 백그라운드 작업이 없고, 출력이 400ms 이상 조용하고, 입력줄에 쓰던 글이 없다.

그 결과 입력창은 답변이 끝난 직후에 이어 쓰는 용도다. 세션의 첫 메시지와, 터미널에 무언가 입력한 뒤의 메시지는 터미널에서 보낸다.

### 실제 사용에서 확인해야 하는 것

코드와 정지 화면으로는 확인하지 못했다.

| 확인할 것 | 걱정 |
|---|---|
| 입력창으로 보통 글, 여러 줄, 슬래시 명령 보내기 | 붙여넣기 방식으로 넣은 글이 뜻대로 들어가는지 |
| 한글 조합 중 Enter | 마지막 글자가 빠지거나 두 번 보내지지 않는지 |
| 답변 뒤에 뜨는 만족도 설문 | 훅 없이 뜨므로 입력창의 글과 Enter가 설문에 들어갈 수 있다 |
| 전체 화면 모드에서 휠 | 터미널이 방향키를 보내 입력창이 잠길 수 있다 |
| 터미널 폭 320px에서 권한 확인 창 | 읽을 수 있는지 |
| 손잡이로 폭 조절, 접고 펴기 | 터미널 글자 수가 다시 맞는지 |
| 상세 화면을 열었다 닫기 | 배치와 스크롤 위치가 돌아오는지 |

### 남은 위험

- 같은 세션을 앱 밖(다른 터미널, 원격 제어)에서 조작하면 앱은 그 입력을 알 수 없다.
- 답변이 끝난 뒤 세션이 사용자 입력 없이 스스로 선택 창을 띄우면 막지 못한다.
- 앱 세션 안에서 돌린 화면 없는 실행이 상태 파일을 덮을 수 있다. 답변 기록 조건이 대부분 막지만 완전하지는 않다.
- 기존 원격 제어 토글에도 "셸이 아닌 프로그램에 글이 들어가는" 같은 종류의 틈이 있다. 정해진 한 문장만 넣는 기능이라 이번에는 건드리지 않았다.

## 11. 2부 규격: 화면 블록

상태: 구현했다. 구현하면서 달라진 것은 13절에 있다.

### 11.1 무엇을 더하는가

1부의 읽기 화면은 답변의 마크다운만 그린다. 그래서 어떤 답변이든 모양이 같다. 2부는 두 가지를 더한다.

- 에이전트가 답변 끝에 화면 블록을 쓴다. 앱은 그 블록을 정해진 부품(수치 카드, 막대 등)으로 그린다.
- 화면 블록에 선택지와 다음 질문을 넣을 수 있다. 사용자가 누르면 앱이 그 문장을 입력창에 채운다. 보내는 것은 사용자가 Enter로 한다.

에이전트는 부품 이름과 글만 쓴다. 앱은 에이전트가 쓴 HTML이나 코드를 실행하지 않는다.

### 11.2 결정

| 번호 | 쟁점 | 결정 | 근거 |
|---|---|---|---|
| E1 | 표기 | 한 줄에 부품 하나. `이름: 칸 \| 칸` 모양 | 터미널에 그대로 보여도 읽힌다. JSON보다 짧고 덜 틀린다 |
| E2 | 부품 이름 | 영어 소문자 한 벌(`stat`, `bar` 등). 내용은 사용자의 언어로 쓴다 | 한 대상에 이름이 하나다. 화면 언어(한국어·영어)와 무관하다 |
| E3 | 블록 수 | 답변 하나에 화면 블록 하나. 여러 개면 마지막 것만 그리고 나머지는 보통 코드로 그린다 | 답변이 화면 블록으로 채워지는 것을 막는다 |
| E4 | 틀린 줄 | 모르는 줄은 보통 글 한 줄로 그린다. 아는 부품이 하나도 없으면 블록 전체를 보통 코드로 그린다 | 해석이 실패해도 내용이 사라지지 않는다 |
| E5 | 줄 안 꾸밈 | 없다. 굵게와 코드 표시도 글자 그대로 보인다 | 부품이 이미 강조 역할을 한다. 해석이 단순해진다 |
| E6 | 단추의 동작 | 입력창에 채우기만 한다. 단추에 보이는 글과 채우는 글은 항상 같다 | 보이지 않는 글이 터미널에 들어갈 길을 없앤다 |
| E7 | 단추가 사는 범위 | 마지막 답변의 단추만 누를 수 있다. 지난 답변의 단추는 흐리게 보이고 눌리지 않는다 | 지난 선택지는 지금 상황과 맞지 않을 수 있다 |
| E8 | 쓰던 글 | 입력창에 쓰던 글이 있으면 단추는 채우지 않고 안내만 보인다 | 사용자가 쓴 글을 지우지 않는다 |
| E9 | 지시문 | 앱 세션에만 붙인다. `MARU_NO_SURFACE=1`이면 붙이지 않는다 | 화면 블록은 읽기 화면이 있어야 쓸모가 있다 |
| E10 | 지시문이 꺼진 세션의 블록 | 답변에 화면 블록이 있으면 그대로 그린다 | 그리는 쪽은 해가 없다 |

### 11.3 표기

언어 이름이 `maru-surface`인 코드 블록이다. 최종 답변의 끝에 쓴다.

````text
```maru-surface
title: 읽기 화면 1부 점검
stat: 앱 시험 | 448 | 실패 0
stat: 스크립트 시험 | 6 | 모두 통과
bar: 구현 단계 | 6 / 6
bar: 실제 사용 확인 | 1 / 7
kv: 브랜치 | main
kv: 커밋 | 9b6662e
warn: 설치된 앱은 아직 새 빌드가 아닙니다.
table: 남은 확인
| 항목 | 상태 |
|---|---|
| 한글 조합 중 Enter | 확인 전 |
| 만족도 설문 | 확인 전 |
choice: 다음에 무엇을 할까요?
- 설치된 앱을 새 빌드로 교체해
- 커밋만 해
next: 남은 위험을 자세히 알려 줘
next: 2부 범위를 다시 보여 줘
```
````

부품별 속성은 이렇다.

| 부품 | 줄 모양 | 그리는 모양 | 제한 |
|---|---|---|---|
| 제목 `title` | `title: 글` | 화면 블록의 머리글 | 1개, 60자 |
| 부제 `sub` (17절) | `sub: 글` | 제목 바로 아래의 흐린 한 줄. `title` 이 없어도 그린다 | 1개, 120자 |
| 구역 머리 `section` (17절) | `section: 제목 \| 설명` (설명은 생략 가능) | 뒤에 오는 부품들 위의 작은 머리. 뒤의 부품을 감싸지 않는다 | 6개. 제목 60자, 설명 120자 |
| 카드 `card` (17절) | `card: 제목 \| 설명 \| 꼬리표` (설명·꼬리표는 생략 가능) | 연달은 줄은 한 격자(한 줄 3칸, 좁으면 2칸·1칸). 꼬리표, 제목, 설명 순 | 블록 전체 9개. 제목 40자, 설명 160자, 꼬리표 24자 |
| 수치 카드 `stat` | `stat: 이름 \| 값 \| 보조 글` (보조 글은 생략 가능) | 이어진 줄을 한 줄에 최대 4장씩 나란히 놓는다. 값은 큰 글자 | 8장. 이름 30자, 값 20자, 보조 글 40자 |
| 막대 `bar` | `bar: 이름 \| 값 / 최대` 또는 `bar: 이름 \| 72%` | 가로 막대와 오른쪽 숫자. 이어진 줄은 한 묶음 | 8개. 값은 0 이상 최대 이하로 맞춘다. 숫자가 아니면 보통 글로 그린다 |
| 항목-값 목록 `kv` | `kv: 항목 \| 값` | 두 칸 목록. 이어진 줄은 한 묶음 | 12줄. 항목 30자, 값 200자 |
| 강조 상자 `note`, `warn` | `note: 글`, `warn: 글` | 왼쪽에 세로 띠가 있는 상자. `warn`은 띠 색만 다르다 | 4개, 각 300자 |
| 표 `table` | `table: 제목`(제목은 생략 가능) 다음 줄부터 마크다운 표 | 1부의 표와 같은 함수로 그린다 | 1개, 6열 20행 |
| 선택지 `choice` | `choice: 질문` 다음 줄부터 `- 선택지` | 질문과 세로로 놓인 단추 | 1개, 선택지 2~5개, 각 120자 |
| 다음 질문 `next` | `next: 문장` | 블록 맨 아래에 가로로 놓인 작은 단추 | 3개, 각 120자 |

- 블록 전체는 60줄, 6000자까지 읽는다(17절에서 40줄, 4000자에서 올렸다). 넘는 줄은 그리지 않고 "더 있음. 터미널에서 확인"을 보인다.
- 칸을 나누는 글자는 `|`이다. 글에 `|`를 쓰려면 `\|`로 쓴다.
- 선택지와 다음 질문의 글은 한 줄이다. 앱은 채우기 전에 1부의 정리 함수(`readCleanSend`)로 제어 문자를 지운다.

### 11.4 지시문 초안

`prompts/read-surface.md`에 두고 `scripts/maru-claude.sh`가 앱 세션에 `--append-system-prompt`로 붙인다. 붙이는 조건은 기록 훅(talk-log)을 붙이는 조건과 같고, `MARU_NO_SURFACE=1`이면 붙이지 않는다. 모델이 정확히 따르도록 영어로 쓴다.

2026-11-26에 지시문을 고쳤다. 아래 초안은 처음 판이고, 지금 판은 `prompts/read-surface.md`가 기준이다. 바뀐 점은 셋이다.

- 처음 판은 화면 블록을 "써도 된다"고 했다. 지금 판은 숫자·상태·비교·여러 사실·위험·결정이 있는 답변이면 화면 블록을 쓰라고 한다. 사용자가 답변이 평소 글 양식 그대로 나온다고 알려 왔기 때문이다.
- 지금 판은 답변의 모양을 정한다. 결론 한두 문장, 문장이 필요한 설명, 화면 블록 순서다. 같은 사실을 마크다운 표나 목록으로 또 쓰지 않게 한다.
- 지금 판은 항목마다 쓰는 경우를 적는다(예: 셋 이상의 비교는 `table`, 최댓값이 있는 비율은 `bar`). 공개 예제(CopilotKit의 a2ui-playground)가 "일에 맞는 부품을 고르는 규칙"을 지시문에 넣는 방식을 참고했다.

길이는 약 150토큰에서 약 450토큰으로 늘었다(2019바이트). 세션마다 이만큼 든다.

```text
The app shows your final answer in a reading view that draws markdown.
When a final answer has key numbers, a status summary, or a decision for the user, you may end it with ONE fenced code block with the language maru-surface. Do not use it for short answers or plain conversation.
One item per line, plain text only, at most 30 lines:
title: text
stat: label | value | note
bar: label | value / max
kv: label | value
note: text
warn: text
table: title, followed by markdown table rows
choice: question, followed by 2 to 5 lines "- option"
next: text (up to 3 lines)
An option or next line is the exact message the user would send to you. Write it in the user's language. Keep each under 120 characters and do not start one with !, / or #. Do not put commands or secrets in it. The app does not send it. The user reads it and sends it.
```

### 11.5 안전 규칙

| 위험 | 대응 |
|---|---|
| 화면 블록의 글이 앱의 단추나 경고를 흉내 낸다 | 화면 블록은 테두리 상자 안에만 그린다(17절에서 점선을 실선으로 바꿨다). 상자 맨 아래 오른쪽에 출처 표지 "에이전트가 만든 화면"을 항상 보인다. 앱의 상태 줄, 권한 대기 띠, 입력창은 이 상자 밖에 있다. `warn`은 권한 대기 띠의 색과 모양을 쓰지 않는다 |
| 단추가 사용자 모르게 글을 보낸다 | 단추는 입력창의 글만 바꾼다. 보내는 길(`read:send`)을 부르지 않는다. 1부의 판정(`readCanSend`)은 바꾸지 않는다 |
| 단추에 보이는 글과 들어가는 글이 다르다 | 값은 하나뿐이다. 보이는 글이 곧 채우는 글이다 |
| 외부 글에서 온 문장이 선택지가 된다 | 사용자가 입력창에서 글을 읽고 Enter를 눌러야 나간다. 출처 표지가 앱이 권하는 것이 아님을 알린다 |
| 블록이 HTML이나 코드를 담는다 | 모든 글을 textContent로만 넣는다. 링크, 이미지, 색 지정, 크기 지정을 받지 않는다. 색은 style.css의 변수만 쓴다 |
| 큰 블록이 화면을 느리게 한다 | 11.3의 제한을 해석 함수에서 지킨다. 해석 함수는 예외를 던지지 않는다 |
| 사용자의 질문에 든 블록이 화면이 된다 | 답변(assistant) 항목의 블록만 화면으로 그린다 |
| 지난 답변의 선택지를 누른다 | 마지막 답변의 단추만 누를 수 있다(E7) |

### 11.6 구현 단계

| 단계 | 바꿀 파일 | 끝 조건 | 시험 |
|---|---|---|---|
| 1. 해석 | `app/lib.js`, `app/test.js` | 순수 함수 `surfaceParse(text)`가 11.3대로 부품 목록을 낸다. `talkParse`가 답변의 마지막 `maru-surface` 코드 블록을 `surface` 블록으로 바꾼다 | 단위 시험: 부품마다 정상 줄, 칸 부족, `\|` 처리, 제한 초과, 모르는 줄, 부품 없음, 블록 둘, 질문 안의 블록 |
| 2. 지시문 | `prompts/read-surface.md`(새 파일), `scripts/maru-claude.sh`, 스크립트 시험 | 앱 세션의 실행 인자에 지시문이 붙는다. `MARU_NO_SURFACE=1`이면 붙지 않는다. 앱 세션이 아니면 붙지 않는다 | 임시 폴더에서 가짜 `claude`로 인자를 확인한다 |

### 11.7 이번에 하지 않는 것

입력 폼, 차트, 이미지, 링크, 단추가 바로 보내는 동작, HTML 아티팩트, 앱이 만드는 카드, 턴 도중에 그리는 것.

### 11.8 구현 전에 알 수 없는 것

- 모델이 지시문을 얼마나 자주 따르는지. 너무 자주 쓰거나 전혀 쓰지 않을 수 있다. 실제 세션에서 써 봐야 안다.
- 이어 연 세션(`--resume`)과 스쿼드 총괄 세션(`--agent`)에서 `--append-system-prompt`가 같이 듣는지. 2단계에서 확인한다.

## 12. 2부 추가: 기본 배치와 첫 메시지

사용자가 2부 도중에 정했다.

### 12.1 기본 배치

- 저장된 상태가 없는 작업 공간은 읽기 화면이 켜지고 터미널이 접힌 채 시작한다.
- 2026-11-26 변경: 앱을 켤 때는 저장값에서 터미널 폭만 잇는다(`readStoreStart`). 읽기 화면 켜짐과 터미널 접힘은 언제나 기본값으로 시작한다. 예전에 끄거나 편 작업 공간이 그 상태로 다시 열려서 기본 화면이 지켜지지 않았기 때문이다. 실행 중에 바꾼 배치는 그 실행 동안만 유지된다.
- 터미널이 접힌 동안에는 오른쪽 카드 열(스쿼드, 할 일)을 다시 보인다. 터미널을 펴면 터미널이 그 자리를 쓴다.

### 12.2 첫 메시지를 입력창으로 보내기

1부는 세션의 첫 메시지를 터미널에서만 보내게 했다. 터미널이 접힌 채 시작하므로 입력창에서도 첫 메시지를 보낼 수 있게 한다. 답변 직후에 보내는 기존 판정(`readCanSend`)은 바꾸지 않는다. 첫 메시지만 다루는 길을 따로 더한다.

걱정은 세션을 막 띄운 직후에 뜨는 창이다(폴더 신뢰 확인, MCP 서버 승인, 로그인 등). 이 창들은 훅을 거치지 않아서 앱이 상태로는 알 수 없다. 그래서 앱이 터미널 화면을 직접 읽어 Claude Code의 입력줄 상자가 보일 때만 보낸다.

순서는 이렇다.

1. 사전 판정(`readCanSendFirst`): 앱이 이 터미널에서 세션을 띄웠다. 앱이 기억한 프로세스가 앞에 있다. 이 터미널을 띄운 뒤 훅 기록이 하나도 없다. 세션을 띄운 뒤 터미널에 쓴 것이 없다. 출력이 1초 이상 조용하다. 세션이 뜬 지 2초가 지났다. 백그라운드 작업과 쓰던 글이 없다.
2. 화면 사전 확인(`promptBoxCheck`): 커서가 입력줄 상자(위아래 경계선) 안에 있고, 상자 밖에 선택 창의 흔적이 없다. 아니면 아무것도 쓰지 않고 거부한다(이유 `first-screen`).
3. 글만 붙여넣는다. Enter는 보내지 않는다.
4. 화면 사후 확인: 최대 1.5초 동안, 붙여넣은 글이 입력줄 상자 안에 보이는지 확인한다.
5. 그 사이 터미널에 다른 입력이 없었고 같은 작업 공간이면 Enter를 보낸다. 아니면 Enter를 보내지 않고 알린다(이유 `first-unsent`). 앱은 남은 글을 지우지 않는다.

화면 판정은 main이 순수 함수로 한다. 렌더러는 화면 글만 넘긴다.

남는 위험은 이렇다.

- 사전 확인과 붙여넣기 사이(수 ms)에 창이 새로 뜨면 글이 그 창에 들어간다. Enter는 가지 않는다. 그 창이 붙여넣은 글자를 선택 키로 받는지는 확인하지 못했다.
- Claude Code가 입력줄 모양을 바꾸면 판정이 거부 쪽으로 실패한다. 안전하지만 첫 메시지를 입력창으로 보낼 수 없게 된다.
- 접힌 터미널 안에 시작 창이 떠 있으면 사용자에게 보이지 않는다. 그래서 `first-screen`으로 거부할 때 터미널 띠를 강조하고 "터미널을 열어 확인하세요"를 보인다.

## 14. 3부: 턴 도중의 실시간 표시

상태: 구현했다. 설치된 앱에는 아직 반영하지 않았다.

### 14.1 무엇을 더하는가

지금 읽기 화면은 턴이 끝난 뒤에 최종 답변만 그린다. 그래서 질문을 보낸 뒤 세션이 실제로 일하고 있는지 읽기 화면에서는 알 수 없다. 턴 도중에 두 가지를 보인다.

- 활동 목록: 세션이 도구를 부를 때마다 한 줄이 생긴다(무슨 도구로 무엇을 하는지, 끝났는지, 걸린 시간).
- 터미널 미리보기: 터미널 화면에서 입력줄 위의 마지막 몇 줄을 글자 그대로 보인다. 세션이 쓰고 있는 글이 여기에 실시간으로 보인다.

턴이 끝나면 지금처럼 최종 답변을 마크다운으로 그리고, 활동 목록은 한 줄 요약으로 접는다.

### 14.2 직접 확인한 것(화면 없는 실행 한 번)

| 확인한 것 | 결과 |
|---|---|
| 도구를 부르기 직전 훅(PreToolUse)의 입력 | 도구 이름(`tool_name`), 도구 입력(`tool_input`), 호출 식별값(`tool_use_id`)이 있다 |
| 도구가 끝난 뒤 훅(PostToolUse)의 입력 | 위에 더해 걸린 시간(`duration_ms`)과 결과(`tool_response`)가 있다 |
| 도구 호출 사이의 중간 글을 훅에서 얻을 수 있는가 | 얻지 못했다. 훅 입력에 없고, 그 시점의 대화 기록 파일 끝에도 없었다 |

그래서 글자가 써지는 모습을 마크다운으로 그리는 길은 없다. 중간 글은 터미널 화면에서만 볼 수 있으므로 터미널 미리보기로 보인다.

### 14.3 활동 기록 파일

- 경로: `data/state/app/<세션 id>.act.jsonl`. 기록 파일(talk)과 같은 조건에서만 쓴다. 끄는 변수도 같다(`MARU_NO_TALK_LOG=1`).
- 쓰는 곳: `scripts/talk-log.sh` 에 `pre`, `post` 동작을 더한다. 질문 훅(`user`)이 돌 때 이 파일을 비운다. 즉 한 턴의 활동만 담는다.
- 한 줄: `{"v":1,"at":<초, 소수>,"k":"pre"|"post","id":"<호출 식별값>","tool":"<도구 이름>","sum":"<요약>","ms":<걸린 시간>,"err":true}`. `sum` 은 `pre` 에만, `ms` 와 `err` 는 `post` 에만 있다.
- 요약(`sum`)은 160자까지다. 도구별로 정한 칸만 쓴다.

| 도구 | 요약에 쓰는 것 |
|---|---|
| Bash | `description`. 없으면 명령의 첫 낱말만 쓴다. 명령은 `shlex` 로 나눈다(나누다 실패하면 빈 글). 앞의 `NAME=값` 낱말은 건너뛴다. 그다음 첫 낱말의 마지막 경로 마디가 `[A-Za-z0-9_.+-]{1,32}` 에 전부 맞을 때만 쓰고, 아니면 빈 글이다. 앞머리가 `(`, `{`, `$`, 백틱, 따옴표여서 이 규칙에 맞지 않는 명령도 빈 글이다. 명령 전체는 쓰지 않는다 |
| Read, Edit, Write, NotebookEdit | 파일 경로의 마지막 두 마디 |
| Grep, Glob | `pattern`. 80자까지 |
| WebFetch | 주소의 호스트 이름만 |
| WebSearch | `query`. 80자까지 |
| Agent, Task | `description` |
| Skill | 스킬 이름 |
| 그 밖 | 쓰지 않는다(도구 이름만 보인다) |

- 비밀값 모양 거르기: Bash(`description`, 첫 낱말), Grep, Glob, WebSearch, Agent, Task 의 요약에 아래 덩어리가 있으면 요약을 빈 글로 한다. 덩어리는 공백 없는 영숫자·`_`·`-` 가 24자 이상 이어진 글이고, 숫자와 글자가 모두 들어 있다. 예는 `sk-ant-abc123…` 이다. `description` 이 이 덩어리를 담으면 명령의 첫 낱말로 되돌아가지 않고 빈 글로 한다.
- 제한: 300줄, 256KB. 넘으면 앞에서부터 버려 250줄, 200KB 이하로 줄인다. 모드 600. 작업 공간을 닫을 때와 72시간 정리 때 기록 파일과 함께 지운다.
- 줄이기: 평소에는 파일을 읽지 않고 `O_APPEND` 로 한 줄만 덧붙인다. 크기가 16KB 를 넘을 때만 파일을 읽어 줄 수와 크기를 확인한다. 이 스크립트가 쓰는 한 줄은 가장 짧아도 59바이트이므로, 300줄은 17,700바이트를 넘는다. 그래서 16KB 기준에서도 300줄 제한이 늦게 걸리지 않는다. 읽기와 줄이기는 `<세션 id>.act.lock` 파일의 `flock` 안에서 한다. 잠금을 잡지 못하면(0.5초 동안 다시 시도) 줄이기를 건너뛰고 덧붙이기만 한다. 질문 훅(`user`)의 비우기도 같은 잠금을 쓰되, 잡지 못해도 비운다. 잠금 파일은 모드 600이고 크기가 0이다. 심볼릭 링크는 거부한다. 앱의 정리 대상(`*.act.jsonl`)과 이름이 다르므로 비운 뒤에도 지우지 않는다.
- 큰 입력: 훅 입력은 1MB(1,048,576바이트)까지만 읽는다. 1MB 이상이어서 JSON 해석이 실패하면 앞쪽 글에서 `session_id`, `tool_use_id`, `tool_name` 을 정규식으로 찾는다. 셋 다 찾으면 `sum` 이 빈 `pre` 줄 또는 `ms` 없는 `post` 줄을 쓴다. 하나라도 못 찾으면 아무것도 쓰지 않는다. 1MB 미만의 깨진 JSON 도 쓰지 않는다.
- 시간(측정값): 훅 한 번은 `pre` 20회를 이어서 돌린 시간을 20으로 나눠 쟀다. 이 맥에서 고치기 전 약 97ms, 고친 뒤 약 80ms 다(다섯 번 되풀이한 중앙값. 다른 작업이 겹치면 100ms 이상 흔들린다). 시간의 대부분은 python 시작이다. `head`, `wc`, `tr`, `dirname`, `mkdir` 호출을 없애고 python 을 `-I -S` 로 띄워 줄였다.

### 14.4 화면

- 마지막 항목이 질문이고 세션이 작업 중이거나 답을 기다리는 동안, 질문 아래에 활동 상자를 보인다.
- 활동 상자의 머리: "작업 중"과 지난 시간.
- 활동 줄: 상태 표시(진행 중, 끝남, 실패), 도구의 종류(명령, 읽기, 고치기, 찾기, 웹, 하위 에이전트, 그 밖은 도구 이름), 요약, 걸린 시간. 최근 8줄을 보이고 앞의 것은 "앞의 N개"로 접는다.
- 터미널 미리보기: 활동 줄 아래에 고정 폭 글자로 최대 8줄. 표지 "터미널에 지금 보이는 글"을 붙인다. 0.5초마다 다시 읽는다. 터미널이 펴져 있으면 보이지 않는다.
- 턴이 끝나면 활동 상자는 답변 위의 한 줄("도구 7번 · 1분 22초")로 접힌다. 누르면 펼친다. 다음 질문을 보내면 사라진다.
- 모든 글은 textContent로만 넣는다. 활동 상자와 미리보기에는 누를 것이 없다(접기 단추만 있다).

### 14.5 안전

| 위험 | 대응 |
|---|---|
| 요약에 비밀값이 남는다 | 명령 전체와 파일 내용, 도구 결과는 기록하지 않는다. 14.3의 칸만 쓴다. Bash 첫 낱말은 `shlex` 로 나눠 `NAME=값` 을 건너뛰고, 마지막 경로 마디가 `[A-Za-z0-9_.+-]{1,32}` 에 맞을 때만 쓴다. 따옴표 안의 값 조각은 쓰지 않는다. 비밀값 모양 글(영숫자·`_`·`-` 24자 이상 덩어리에 숫자와 글자가 모두 있음)이 든 요약은 빈 글로 한다. `pattern` 과 `query` 는 80자까지 쓴다 |
| 큰 입력이 훅을 막거나 글을 새긴다 | 입력은 1MB 까지만 읽는다. 해석이 실패하면 앞쪽에서 세 값(`session_id`, `tool_use_id`, `tool_name`)만 정규식으로 찾고, 요약과 `ms` 는 쓰지 않는다 |
| 훅이 세션을 늦춘다 | 도구 호출마다 두 번 돈다. 제한 시간 5초. 실제로는 한 번에 약 80ms 가 든다(측정값, 14.3). 외부 명령을 쓰지 않고 python 한 번만 띄운다. 실패해도 0으로 끝나고 아무것도 출력하지 않는다 |
| 병렬 훅이 파일을 깨거나 줄을 흘린다 | 평소에는 `O_APPEND` 로 한 번에 한 줄을 덧붙인다. 줄이기는 `<세션 id>.act.lock` 의 `flock` 안에서 한 번에 하나만 한다. 줄이기 도중에 다른 훅이 덧붙인 줄은 드물게 사라질 수 있다(읽은 뒤 크기가 바뀌면 다시 읽어 창을 줄였다). 표시용 기록이므로 받아들인다 |
| 미리보기가 권한 확인 창의 글을 보인다 | 글자만 보인다. 누를 수 없다. 답은 터미널에서 한다는 기존 안내를 그대로 둔다 |
| 미리보기의 글이 앱의 안내를 흉내 낸다 | 고정 폭 글자, 점선 상자, 표지로 구분한다 |
| 입력 판정이 바뀐다 | 입력 판정(`readCanSend`, `readCanSendFirst`)은 건드리지 않는다. 활동 기록은 판정에 쓰지 않는다 |

## 15. 3부: 입력창에 이미지 붙이기

상태: 구현했다. 설치된 앱에는 아직 반영하지 않았다.

### 15.1 직접 확인한 것(실제 세션 화면, 메시지는 보내지 않음)

| 확인한 것 | 결과 |
|---|---|
| 이미지 파일의 경로만 붙여넣는다 | 입력줄에 `[Image #1]`이 생긴다. 세션이 그 파일을 첨부로 받는다 |
| 이어서 글을 붙여넣는다 | `[Image #1] 글` 모양으로 이어진다 |
| 글과 경로를 한 번에 붙여넣는다 | 첨부가 되지 않고 경로가 글자로 남는다 |

그래서 이미지는 경로만 따로 붙여넣고, 글은 그 뒤에 붙여넣어야 한다.

### 15.2 동작

- 입력창에서 붙여넣기를 하면 앱(main)이 클립보드의 이미지를 직접 읽어 `data/state/app/paste/` 아래에 PNG 파일로 저장한다. 렌더러는 경로를 정하지 못한다. 렌더러는 main이 준 표(token)만 가진다.
- 입력창 위에 첨부 표시("이미지 1 ×")가 생긴다. ×로 뺀다. 한 메시지에 4장까지, 한 장은 10MB까지다.
- 보낼 때 main은 기존 판정(`readCanSend` 또는 첫 메시지 판정)을 통과한 뒤 아래 순서로 넣는다. 단계마다 터미널 화면을 읽어 확인한다.
  1. 입력줄 상자가 비어 있는지 확인한다.
  2. 이미지마다 경로만 붙여넣고, 입력줄에 `[Image #N]` 표시가 하나 늘었는지 확인한다.
  3. 글이 있으면 글을 붙여넣고, 입력줄에 표시와 글이 보이는지 확인한다.
  4. 그 사이 다른 입력이 없었고 화면을 읽은 뒤로 출력이 없었으면 Enter를 보낸다.
- 어느 단계든 확인하지 못하면 Enter를 보내지 않고 알린다. 넣은 것은 터미널 입력줄에 남는다. 앱은 지우지 않는다.
- 이미지가 없는 메시지는 지금 경로 그대로 보낸다(바뀌지 않는다).
- 저장한 파일은 24시간 뒤 앱을 켤 때 지운다. 모드 600이다.

### 15.2.1 바뀐 점(붙이기 판정·바이트 길·미리보기·배치)

- 이미지 판정은 `pasteIsImage`가 한다. 글 항목이 같이 와도 이미지로 다룬다. 브라우저·메신저의 "이미지 복사"는 `text/html` 글 항목을 함께 싣기 때문이다.
- `text/plain`이 있어도 `text/html`과 `text/rtf`가 둘 다 없으면 이미지로 다룬다. 파일 관리자에서 이미지 파일을 복사하면 파일 이름 글이 같이 온다.
- `text/plain`과 함께 `text/html` 또는 `text/rtf`가 있으면 글로 다룬다. 표 계산·문서 앱에서 복사한 글이다.
- 이미지를 받는 길은 둘이다. 렌더러는 paste 이벤트의 파일(10MB 이하)을 먼저 `read:paste-bytes`로 보낸다. main이 `noimage`를 돌려주거나 파일이 없으면 기존 `read:paste-image`를 쓴다.
- `read:paste-bytes`는 받은 바이트를 파일로 쓰지 않는다. `nativeImage.createFromBuffer`로 풀고 PNG로 다시 인코딩한 것만 쓴다. 두 길은 저장 함수(`pasteImageSave`)를 같이 쓴다. busy·full·가짜 응답 규칙도 같다.
- main은 저장에 성공하면 높이 144px 이하의 `data:` PNG 미리보기(`thumb`)를 결과에 더한다. 400000자를 넘으면 뺀다. 렌더러는 `data:image/png;base64,`로 시작하는 것만 `<img>`에 쓴다.
- CSP는 바꾸지 않았다. `img-src`가 `blob:`을 허용하지 않아 이전의 `blob:` 미리보기는 한 번도 뜨지 않았다. `blob:` 코드는 지웠다.
- 첨부 미리보기는 입력 상자 안쪽 위에 둔다. 높이 72px, 너비는 비율대로 최대 128px이다. 오른쪽 위 구석에 지우기 단추(×)가 겹친다.
- 개발용 화면 `MARU_APP_UI=readatt`는 `read`와 같고, 입력창에 가짜 첨부 2개가 붙어 있다.

### 15.3 안전

| 위험 | 대응 |
|---|---|
| 렌더러가 임의의 파일 경로를 터미널에 넣게 한다 | 경로는 main이 만든 파일만 쓴다. 렌더러가 주는 것은 main이 준 표뿐이고, main이 표를 경로로 바꾼다 |
| 여러 번 나눠 넣는 사이에 확인 창이 뜬다 | 단계마다 화면을 확인한다. 확인하지 못하면 멈춘다. Enter는 마지막 확인 뒤에만 보낸다 |
| 이미지가 디스크에 남는다 | 이 컴퓨터의 `data/` 안에만 둔다. 24시간 뒤 지운다 |

### 15.4 입력창의 Enter 처리(바뀐 점)

- 이전에는 한글 조합 중의 Enter와 조합이 끝난 뒤 50ms 안의 Enter를 keydown에서 그냥 돌려보냈다. 브라우저 기본 동작이 줄바꿈을 넣어, 빠르게 치고 Enter를 누르면 보내지지 않았다.
- 이제 keydown은 마지막 Enter의 시각·보통 Enter 여부·반복 여부를 적는다. 조합 중의 Enter도 적는다.
- 줄바꿈이 들어가려는 순간(`beforeinput`의 `insertLineBreak`·`insertParagraph`)에 `enterLineBreakVerdict`가 판정한다.
  - `newline`: Enter에서 온 줄바꿈이 아니거나(400ms 초과) Shift·Alt·Ctrl·Meta를 누른 Enter다. 그대로 둔다.
  - `block`: 반복 Enter이거나 단추로 채운 직후(500ms 안, 또는 채울 때 눌린 Enter를 떼기 전)다. 줄바꿈도 보내기도 하지 않는다.
  - `send`: 줄바꿈을 막고 한 틱 뒤에 보낸다. 그래서 조합이 끝난 글을 읽는다. `beforeinput`을 취소할 수 없으면 다음 `input`에서 줄바꿈 한 글자를 지우고 보낸다.
- 조합이 끝난 보통 Enter는 이전처럼 keydown에서 보낸다. 같은 Enter 한 번은 보내기를 두 번 일으키지 않는다.
- Enter가 변환 확정만 하고 줄바꿈을 만들지 않는 입력기(일본어 등)는 `beforeinput` 줄바꿈이 오지 않으므로 보내지 않는다.

## 16. 3부: 세션 다시 시작 표지와 슬래시 명령

상태: 구현했다. 설치된 앱에는 아직 반영하지 않았다.

### 16.1 직접 확인한 것(실제 세션)

| 확인한 것 | 결과 |
|---|---|
| 입력줄에 `/clear`를 붙여넣고 Enter를 보낸다 | 명령으로 실행된다 |
| `/clear` 때 도는 훅 | 세션 끝 훅(SessionEnd, `reason: clear`) 다음에 세션 시작 훅(SessionStart, `source: clear`)이 돈다. 세션 id가 바뀐다 |
| `/compact` 때 도는 훅 | 압축 전 훅(PreCompact, `trigger: manual`) 다음에 세션 시작 훅(SessionStart, `source: compact`)이 돈다. 세션 id는 그대로다 |
| 이 명령들에서 질문 훅과 종료 훅이 도는가 | 돌지 않는다 |

그래서 지금 앱은 `/clear` 뒤에 세션이 바뀐 것을 다음 질문이 올 때까지 모른다. 읽기 화면이 비워지지 않는 까닭이다.

### 16.2 세션 시작 표지

- 훅: 세션 시작(SessionStart)과 압축 전(PreCompact)에 `scripts/talk-log.sh start`, `scripts/talk-log.sh compact`를 붙인다.
- 파일: `data/state/app/<앱이 터미널에 준 세션 값>.sess`. 내용은 `{"v":1,"at":<초, 소수>,"sid":"<세션 id>","source":"startup"|"resume"|"clear"|"compact"|"precompact"}` 한 줄이다. 매번 통째로 바꿔 쓴다.
- 쓰는 조건은 기록 파일(talk)과 같다.
- 앱은 이 표지를 읽어 아래처럼 쓴다.
  - 표지가 상태 기록보다 새것이면 표지의 세션 id로 대화 기록을 읽는다. `/clear` 뒤에 읽기 화면이 바로 비워진다.
  - 표지가 `precompact`이면 "대화를 압축하는 중"을 보이고 입력창을 잠근다.
  - 표지가 `compact`이면 대화 끝에 "대화를 압축했습니다" 한 줄을 보인다.
  - 표지가 상태 기록보다 새것이면(다시 시작한 뒤 아직 질문이 없다) 입력창은 첫 메시지 길로 보낸다. 화면에서 빈 입력줄을 확인하고, 붙여넣고, 다시 확인한 뒤 Enter를 보낸다. "터미널에 입력이 없었다"의 기준점은 세션을 띄운 때가 아니라 표지의 시각이다.

### 16.3 입력창의 슬래시 명령

- 입력창의 글이 `/`로 시작하면 앱은 화면을 확인하며 보내는 길을 쓴다(붙여넣기, 입력줄에 그 글이 보이는지 확인, Enter). 답변 직후 길의 한 번에 보내기를 쓰지 않는다.
- 목록: 입력창에 `/`를 치면 입력창 위에 목록이 뜬다. 위아래 키로 고른다. Esc로 닫는다.
  - 기본 명령: `/clear`, `/compact`.
  - 스킬과 사용자 명령: 작업 폴더와 사용자 폴더의 `.claude/skills/*/SKILL.md`, `.claude/commands/*.md`에서 읽는다. 폴더마다 200개까지 읽고, 목록은 100개까지다.
  - 스킬 이름은 폴더 이름이다(frontmatter `name`은 폴더 이름과 같을 때만 쓴다). 사용자 명령 이름은 파일 이름이다. 설명은 frontmatter에서 읽는다.
  - 알려진 내장 명령(`/model`, `/config`, `/resume`, `/permissions`, `/mcp`, `/plan`, `/init`, `/review` 등 62개)과 이름이 같은 스킬·사용자 명령은 목록에서 뺀다. `clear`와 `compact`와 같은 이름도 뺀다.
- 허용 목록: main이 명령 목록(캐시)을 스스로 구한다. 보낼 글의 첫 낱말이 그 목록의 이름과 정확히 같을 때만 보낸다. 렌더러가 준 목록은 믿지 않는다.
  - 목록에 없으면 main은 아무것도 쓰지 않고 `slash-term`으로 거부한다.
  - 이유: Claude Code는 `/mod`처럼 앞머리만 친 글에 Enter를 받으면 명령 안내의 맨 위 후보(`/model`)를 실행한다. 차단 목록으로는 이것을 막을 수 없다.
- 입력창의 Enter와 Tab(글이 한 줄이고 `/`로 시작할 때):
  - 첫 낱말이 목록의 이름과 정확히 같다: 그 항목이 맨 위에서 선택된다. Enter는 바로 보낸다. Tab은 `/이름 `으로 채운다.
  - 앞머리만 맞는다: Enter와 Tab은 고른 항목을 채우기만 한다.
  - 맞는 항목이 없거나 목록이 닫혀 있고 첫 낱말이 목록의 이름이 아니다: Enter는 보내지 않고 "아는 명령이 아닙니다. 목록에서 고르거나 터미널에서 실행하세요."를 보인다.
  - 목록을 아직 받지 못했다: Enter는 보내지 않고 목록이 올 때까지 기다린다.
  - 정렬은 정확히 같은 이름, 앞머리가 맞는 것, 포함하는 것 순이다. 같은 급에서는 기본 명령이 먼저다.
- 거부 이유: `slash-term`은 터미널에서 실행해야 하는 명령(목록에 없는 명령, 내장 명령)에만 쓴다. 세션 조건을 통과하지 못하면 `slash-nosession`("이 세션에서는 명령을 입력창으로 보낼 수 없습니다. 터미널에서 실행하세요.")으로 거부한다.

### 16.4 안전

| 위험 | 대응 |
|---|---|
| 표지를 믿고 확인 창에 글을 넣는다 | 표지는 "첫 메시지 길을 쓴다"만 정한다. 보내기 전후의 화면 확인은 그대로 한다 |
| 표지 뒤에 사용자가 터미널에 입력했다 | 표지 시각 뒤의 입력이 있으면 보내지 않는다 |
| 명령 목록의 이름과 설명이 화면을 속인다 | 글자로만 그린다. 이름은 정해진 글자만 받는다. 고르면 입력창에 채우기만 한다 |
| 명령이 창을 열어 접힌 터미널 안에서 기다린다 | 허용 목록에 있는 명령만 보낸다. 알려진 내장 명령은 목록에서 빼고 보내지 않는다. 보낸 명령 뒤에는 터미널에 입력이 있었던 것으로 세어 다음 답변이나 표지가 올 때까지 잠근다 |
| 앞머리만 친 글(`/mod`)을 Enter가 다른 명령(`/model`)으로 실행한다 | 허용 목록에 정확히 있는 이름만 보낸다. 사후 확인에서 상자 밖의 `❯ /…` 안내 줄(고른 후보)의 이름이 보낼 이름과 다르면 Enter를 보내지 않는다. 그 줄이 화면에 없으면 통과한다 |
| 표지가 원래의 busy·waiting 상태를 지운다 | 원래 문맥의 상태가 busy 또는 waiting이면 표지로 문맥을 합성하지 않는다. precompact 표지는 busy로 만든다 |
| 표지의 내용이 거짓이다 | 시각이 지금보다 5초 넘게 뒤이거나, pty가 뜬 시각보다 앞서거나, 파일 mtime과 5초 넘게 다르면 버린다. 표지 뒤 입력의 여유는 50ms이고, 기준 시각은 표지 시각과 앱이 표지를 처음 본 시각 중 앞선 것이다 |

## 17. 화면 블록: 부품 셋과 새 모양

### 17.1 바뀐 점

- 부품 셋을 더했다: `sub`, `section`, `card`. 줄 표기와 상한은 11.3의 표에 있다.
- 줄 상한을 40줄에서 60줄로, 글자 상한을 4000자에서 6000자로 올렸다.
- 부품은 블록에 쓴 순서대로 그린다. `section` 은 그 자리에 머리를 그릴 뿐 뒤의 부품을 감싸지 않는다.
- 연달은 `card` 줄은 한 격자가 된다. 사이에 다른 부품이나 `section` 이 끼면 격자가 둘로 나뉜다.
- 칸 구분, `\|` 이스케이프, 제어 문자 정리, 상한 초과 처리(넘는 것은 버리고 `truncated`)는 `stat`, `kv` 와 같다.
- 지시문(`prompts/read-surface.md`)을 새 부품에 맞게 다시 썼다. 부품마다 고르는 기준을 적었다.

### 17.2 새 모양

- 점선 테두리 상자를 걷어냈다. 화면 블록은 1px 실선(`var(--line)`), 모서리 12px, 안쪽 여백 18px 20px 의 평평한 상자다.
- 출처 표지 "에이전트가 만든 화면"은 상자 맨 아래 오른쪽으로 옮겼다. 11px 흐린 글이고 항상 보인다. 상자의 `aria-label` 도 그대로다.
- `title` 은 18px 굵게. `stat` 칸은 `var(--bg)` 바탕, 이름 12px, 값 22px, 설명 11px.
- `card` 칸은 1px `var(--line)` 테두리, 모서리 8px, 여백 10px 12px 이다. hover 효과와 커서 변화가 없다. 단추가 아니다.
- `next` 단추 줄 위에 안내 글 "이어서 보낼 글 (누르면 입력창에 채워집니다)"(`read.surf.nextnote`)을 둔다. 줄 안의 옛 라벨 "이어서 물어보기"는 그리지 않는다. 문구 키는 남아 있다.

### 17.3 안전

- 새 부품의 글도 모두 `textContent` 로만 넣는다. `card` 는 눌리지 않으므로 입력창을 채우는 길은 `choice` 와 `next` 단추뿐이다.
- `choice` 와 `next` 의 규칙(120자 초과, `!`·`/`·`#` 시작, 잘린 블록, 선택지 5개 초과는 단추가 아님)은 바꾸지 않았다.
- 출처 표지는 아래로 옮겼지만 항상 그린다. 에이전트가 쓴 화면에는 표지가 빠지지 않는다.

## 18. 읽기 화면의 컨텍스트 사용량

### 18.1 파일 형식

- 상태줄 명령(`scripts/usage-status.sh`)이 앱이 띄운 세션에서 `data/state/app/<세션 값>.ctx` 를 쓴다.
- 파일 이름의 세션 값은 `.sess` 파일과 같다(`w.sessionId`).
- 내용은 한 줄 JSON 이다: `{"v":1,"at":<epoch 밀리초>,"pct":<0~100>,"size":<창 크기 토큰>}`.
- `size` 는 없을 수 있다.

### 18.2 읽는 조건

- `L.ctxParse` 가 글을 검사한다. `v` 는 1, `at` 은 유한한 양수, `pct` 는 0~100 의 유한한 숫자여야 한다.
- `size` 는 1 이상 1억 이하의 정수가 아니면 null 로 둔다. 다른 키는 버린다. 4096자를 넘는 글은 읽지 않는다.
- `ctxOf(w)` 는 `sessOf(w)` 와 같은 조심성으로 읽는다. 폴더가 링크면 읽지 않고, 보통 파일이고 4KB 이하일 때만 읽고, mtime 과 크기가 같으면 캐시를 쓴다.
- 개발용·스모크 모드에서는 디스크를 읽지 않는다. 읽기 화면 개발용 모드(`read*`)만 가짜 값 42% 와 1M 을 준다.
- 환경 변수 `MARU_APP_CTX`(0~100)가 있으면 가짜 값의 pct 로 쓴다. 패키지된 앱은 이 변수를 무시한다.
- `L.ctxView` 가 화면 값 `{ pct, level, size }` 를 만든다. `at` 이 지금보다 5초 넘게 뒤이면 null 이다.
- pty 시작 시각보다 1초 넘게 앞선 `at` 도 null 이다. 앞 세션의 낡은 파일이기 때문이다.
- `pct` 는 정수로 반올림한다. 반올림한 값이 90 이상이면 `high`, 70 이상이면 `mid`, 나머지는 `low` 다.
- `talk:get` 의 응답마다 `ctx` 를 더한다. 대화가 그대로(`same`)여도 더한다. 값이 없으면 null 이다.
- 상태 파일 청소와 작업 공간을 닫을 때의 삭제 목록에 `.ctx` 가 들어 있다.

### 18.3 화면 규격

- 위치는 읽기 입력 상자 바로 아래 줄의 오른쪽이다. 같은 줄 왼쪽에는 안내 글(`#read-input-note`)이 온다.
- 안내 글이 없어도 줄 높이(최소 18px)는 그대로다.
- 모양은 폭 64px, 높이 4px 의 막대와 글 `컨텍스트 42% · 1M`(12px, 흐림)이다. 막대의 채움 비율이 pct 다.
- `mid` 면 막대와 글이 `var(--or2)` 다. `high` 면 `var(--or)` 이고 글이 굵다. `low` 는 흐린 색 그대로다.
- 값이 null 이면 요소를 숨긴다.
- 글은 `textContent` 로만 넣는다. 요소에 `role="img"` 와 `aria-label`("컨텍스트 사용량 42퍼센트")를 둔다. 막대는 `aria-hidden` 이고 `aria-live` 는 쓰지 않는다.
- `title` 은 "이 세션이 쓴 컨텍스트 창의 비율입니다. 값은 Claude Code 상태줄이 알려 준 것입니다."(i18n `ctx.title`; 읽기 화면 문구에 제품 이름을 넣지 않는 시험 때문에 `read.` 로 시작하지 않는 키를 쓴다)다.
- 읽기 화면이 대화를 다시 받을 때마다 응답의 `ctx` 로 다시 그린다. 같은 값이면 DOM 을 건드리지 않는다.
- 작업 공간을 바꾸면 표시를 먼저 비우고 새 작업 공간의 응답으로 그린다.

## 19. 작업 중 보내기와 지금 보내기

### 19.1 실측한 사실

- 이 사실은 이 버전의 Claude Code 화면에서 직접 확인했다.
- 작업 중에도 입력 상자는 화면 맨 아래에 그대로 있다.
- 입력 상자가 비어 있으면 `❯` 뒤가 비고 커서 x 는 2 다. 안내 글은 없다.
- 작업 중에 글을 붙여넣으면 그 글이 상자 안에 보인다.
- Enter 를 누르면 글이 대기열에 들어간다. 화면에 `❯ <글>` 줄과 `⎿  Queued · ctrl+x ctrl+s to send now` 줄이 생긴다.
- 대기열에 넣은 뒤 상자는 다시 비고, 흐린 안내 글 `Press up to edit queued messages` 가 보인다. 커서 x 는 2 다.
- 대기열에 글이 있을 때 Ctrl+X Ctrl+S(바이트 `\x18\x13`)를 누르면 진행 중인 작업이 멈추고 대기열의 글이 바로 간다.
- 작업이 끝나면 대기열의 글이 다음 턴으로 저절로 간다.
- 작업 중에는 화면 출력이 계속된다. 그래서 12.2절 첫 메시지 길의 조용함 조건(`lastOutputAt < snapAt`, 150ms)은 작업 중에 성립하지 않는다.
- 권한 확인 창이 뜨면 입력 상자 자리에 선택 창이 그려진다. 입력 상자가 없다.

### 19.2 가장 중요한 원칙

- 앱은 권한 확인 창과 선택 창에 사용자 대신 답하지 않는다.
- 확신이 없으면 보내지 않는다.
- 작업 중에는 언제든 권한 확인 창이 뜰 수 있다. 그 창에 Enter 가 들어가면 기본 선택지("예")가 눌린다.
- 이 기능의 모든 장치는 이 사고를 막는 데 맞춘다.
- 1부의 판정(`readCanSend`, `readCanSendFirst`, `firstSendVerdict`, `promptBoxCheck`, `imgGateVerdict`, `slashAllowed`)은 바꾸지 않았다. "한가할 때 보내기" 규칙도 그대로다. 새 길은 새 함수다.

### 19.3 판정 `L.readCanSendBusy(ctx, { afterPaste })`

- 이 함수는 `readCanSend` 가 이유 `busy` 로 막은 경우에만 부른다.
- 아래를 모두 만족할 때만 `{ ok:true }` 다.
  1. 앱이 띄운 Claude 가 앞에 있다(`hasTerm`, `cc`, 이름 허용 목록, `claudeUp`, `hooked`, 붙여넣기 모드). `readFirstBase` 는 `ux === 'busy'` 를 거부하므로 쓰지 않고, 같은 조건 가운데 필요한 것만 직접 본다.
  2. `ux` 도 `rawState` 도 `waiting` 이 아니다. `waiting` 이면 어떤 경우에도 통과하지 않는다.
  3. 대화 압축 중이 아니다.
  4. `rawState === 'busy'` 이고 `ux === 'busy'` 다. 백그라운드 작업(`bg > 0`)만 남은 경우는 통과하지 않는다.
  5. 상태 기록 시각이 이 pty 시작 뒤다.
  6. `dirty === false` 다(붙여넣은 뒤의 재판정에서는 보지 않는다).
  7. 활동 기록(`.act.jsonl`)을 읽었고, 짝(`post`)이 없는 `pre` 가운데 가장 새 것의 나이가 3000ms 이상이다.
- 7번의 이유: 권한 확인 창은 `pre` 훅 직후에 뜬다. 나이가 3000ms 미만이면 이유 `busy-tool` 이다. 활동 기록을 못 읽으면 이유 `busy-noact` 다.
- 짝 없는 `pre` 의 나이는 순수 함수 `L.actOpenPreAge(items, now)` 가 구한다. 짝 없는 `pre` 가 없으면 `Infinity` 다.
- main 은 활동 기록을 동기로 읽는다(`actOpenAgeOf`). 화면을 받은 같은 틱에서 판정하려면 기다리는 곳이 없어야 하기 때문이다.
- 활동 기록 파일이 없으면 못 읽은 것으로 본다. 질문을 보낸 직후 첫 도구 호출 전까지는 대기열에 넣지 못할 수 있다.

### 19.4 보내는 순서 `readSendBusy(w, text, { now })`

1. 판정을 본다. 통과하면 화면 사진(`readSnapOf`)을 받고 `promptBoxCheck(snap)` 으로 상자가 비고 커서가 입력줄에 있는지 본다. 아니면 이유 `busy-screen` 이고 아무것도 쓰지 않았다.
2. 쓰기 직전에 판정을 다시 본다. 통과하면 붙여넣기(`\x1b[200~…\x1b[201~`)만 쓴다. Enter 는 아직 쓰지 않는다.
3. 최대 1500ms 동안 50ms 마다 화면을 읽는다. 매번 `busySendVerdict` 가 아래 넷을 본다.
   - 같은 작업 공간이고 같은 pty 다.
   - `promptBoxCheck(snap, text)` 가 통과한다(붙여넣은 글이 상자 안에 보인다).
   - 판정(`dirty` 만 빼고)이 계속 통과한다.
   - 붙여넣은 뒤 pty 에 다른 입력이 없다(`ptyInN` 이 붙여넣기 직후 값과 같다).
4. 넷이 모두 참인 화면을 받으면 그 화면을 받은 같은 틱에서 곧바로 `\r` 을 쓴다. 화면을 받은 뒤 `await` 가 한 번도 없다. 조용함은 요구하지 않는다.
5. 시간이 다 되거나 조건이 깨지면 Enter 를 쓰지 않고 이유 `busy-unsent` 를 돌려준다. 붙여넣은 글은 터미널 입력줄에 남고 지우지 않는다. `w.draft` 가 참이라 다음 보내기는 `draft` 로 막힌다.
- `READ_SEND_GAP_MS` 와 `readFirstBusy` 잠금은 첫 메시지 길과 같이 쓴다. 글 정리(`readCleanSend`)와 길이 상한도 같다.
- 이미지 첨부와 슬래시 명령은 작업 중에 보내지 않는다. 지금처럼 `busy` 로 막는다.
- 개발용 화면과 스모크 모드에서는 이 길이 아무것도 쓰지 않고 `busy` 를 돌려준다.

### 19.5 지금 보내기(Cmd+Enter)

- 쉬는 중에는 Cmd+Enter 가 Enter 와 같다.
- 작업 중에는 19.4 로 대기열에 넣는 데 성공했을 때만 이어 간다.
- 화면을 다시 읽어 `nowSendVerdict` 가 아래를 모두 확인하면 `\x18\x13` 을 쓴다. 최대 1500ms 기다린다.
  - 같은 작업 공간이고 같은 pty 다.
  - `promptBoxCheck(snap)` 가 통과한다(상자가 비고 커서가 입력줄에 있다). 흐린 안내 글은 `plain` 에서 빈칸이다.
  - 화면 글(`snap.lines`) 어딘가에 `ctrl+x ctrl+s` 가 있다. 이 버전이 그 키를 알려 줄 때만 쓴다.
  - 상태가 아직 `busy` 이고 `waiting` 이 아니다.
  - 대기열에 넣은 뒤 pty 에 다른 입력이 없다.
- 화면을 받은 같은 틱에서 곧바로 쓴다.
- 확인하지 못하면 키를 쓰지 않고 `{ ok:true, queued:true, now:false }` 를 돌려준다. 글은 대기열에 있다.
- Ctrl+Enter 도 같다. Shift·Alt 조합은 그대로다.

### 19.6 화면

- main 은 `ws:get` 에 불리언 `bs` 를 더한다. `readCanSend` 가 `busy` 로 막았고 `readCanSendBusy` 가 통과하면 참이다.
- `bs` 가 참이고 `ux` 가 `busy` 면 입력창과 보내기 단추를 잠그지 않는다. `waiting` 과 대화 압축 중의 잠금은 그대로다.
- 안내 글에 "작업 중입니다. Enter 는 대기열에 넣고, ⌘Enter 는 지금 보냅니다." 를 보인다. mac 이 아니면 Ctrl+Enter 로 쓴다.
- 보내기 단추의 글은 "대기열에 넣기"로 바뀐다.
- 성공하면 입력창을 비우고 안내 글을 보인다. 대기열에만 넣었으면 "대기열에 넣었습니다. 지금 작업이 끝나면 보내집니다." 다. 지금 보내기까지 했으면 "작업을 멈추고 지금 보냈습니다." 다. 키를 못 썼으면 "대기열에 넣었습니다. 지금 보내기는 하지 못했습니다. 터미널에서 할 수 있습니다." 다.
- 실패 이유 `busy-screen`, `busy-unsent`, `busy-tool` 은 각자 문구가 있다. 앞의 둘은 접힌 터미널 띠를 주황으로 강조한다.
- Cmd+Enter 는 keydown 에서 처리한다. 조합 중이면 무시하고, 길게 눌러 반복되는 것도 무시한다. `readSendNow({ now: true })` 가 한 함수에서 처리하고, 보내는 중 다시 눌러도 두 번 보내지 않는다.
- 개발용 화면 `MARU_APP_UI=readbusy` 는 작업 중 상태에 입력창이 열려 있고 위 안내 글이 보인다. 가짜 응답이라 디스크와 pty 를 건드리지 않는다.

### 19.7 남는 위험

- 화면을 확인한 직후부터 Enter 가 도착하기 전까지 짧은 틈이 있다.
- 이 틈에 확인 창이 뜨면 그 창에 Enter 가 들어갈 수 있다.
- 이 틈을 줄이는 장치는 둘이다. "짝 없는 pre 3초" 규칙과 "같은 틱 쓰기"다.
- 이 위험은 없앨 수 없다. 대기열이 필요 없으면 터미널에서 직접 보내도 된다.
- 지금 보내기(Ctrl+X Ctrl+S)도 같은 틈이 있다. 이 키가 확인 창에 들어가면 어떤 일이 생기는지는 확인하지 못했다.

### 19.8 독립 검토 뒤에 바꾼 것과 남긴 위험

바꾼 것은 넷이다.

- 지금 보내기 키는 화면에 대기열 표시 줄(`⎿  Queued · ctrl+x ctrl+s to send now` 모양)이 있을 때만 쓴다. 대화 글에 같은 낱말이 있어도 통과하지 않는다.
- 작업 중에는 3자 이하의 글과 숫자·y·n 뿐인 글을 보내지 않는다(`busy-short`). 붙여넣은 글이 선택 창의 단축키로 읽힐 수 있기 때문이다.
- 화면 사진을 받는 데 60ms 넘게 걸리면 그 사진을 버리고 다시 읽는다.
- 화면이 쉬는 중으로 보였을 때 누른 Cmd+Enter 는 보통 보내기로만 다룬다. 뜻하지 않게 작업을 끊지 않는다.

남긴 위험은 셋이다. 셋 모두에서 마지막 방어는 화면 확인(입력 상자가 보이고 붙여넣은 글이 그 안에 있다)이다.

- 병렬 서브에이전트가 있으면 한쪽의 권한 대기 기록을 다른 쪽 훅이 작업 중으로 덮어쓸 수 있다. 이때 상태 기록으로는 권한 대기를 알 수 없다.
- 활동 기록의 pre 줄이 빠지면(훅 실패, 줄이기 경쟁) "짝 없는 pre 3초" 규칙이 걸리지 않는다.
- 도구 호출 없이 뜨는 창(실행 중 도구의 추가 허용 창, 한도 선택 창 등)은 pre 기록이 없다.

화면을 확인한 직후부터 Enter 가 도착하기 전까지의 틈은 없앨 수 없다. 이 틈에 창이 뜨면 그 창에 Enter 가 들어갈 수 있다.

## 20. 터미널의 흐린 추천 글

읽기 화면은 터미널을 접어 두므로 입력 상자의 흐린 추천 글이 보이지 않는다. 이 절은 그 글을 읽기 화면 입력창에 보이고 Tab 으로 채우는 방법을 정한다.

### 20.1 읽는 조건

- 읽기 화면이 켜져 있어야 한다.
- 이 작업 공간이 "한가할 때 보내기"가 되는 상태여야 한다. 입력 잠금이 없고, 작업 중이나 권한 대기가 아니다.
- 입력창이 비어 있고 첨부가 없어야 한다.
- 세 조건이 맞을 때만 renderer 가 1초마다 이 작업 공간의 xterm 버퍼에서 화면 사진을 직접 만든다. main 을 거치지 않는다.
- 조건이 깨지면 타이머를 멈추고 추천 글을 지운다. 작업 공간을 바꾸면 바로 지운다.
- 사진을 만드는 코드는 `termSnapNow` 하나다. 첫 메시지 길의 `onReadSnapReq` 도 같은 함수를 쓴다.

### 20.2 거르는 글

- `lib.js` 의 `promptGhost(snap)` 이 판단한다. 순수 함수이고 예외를 던지지 않는다.
- `promptBoxCheck` 사전 확인이 통과하지 않으면 빈 글을 돌려준다.
- 입력줄의 `lines` 글에서 표시(`❯`·`>`)와 뒤 공백(U+00A0 포함)을 뗀 나머지가 후보다. `plain` 의 같은 자리는 비어 있어야 한다.
- 후보는 `readCleanSend` 와 같은 정리를 거친다. 비었거나 200자를 넘으면 빈 글이다.
- `Try "` 와 `Press up` 으로 시작하는 안내 글은 추천이 아니다.
- `!`·`/`·`#` 로 시작하는 글은 명령처럼 보낼 수 있으므로 채우지 않는다.

### 20.3 보이기와 채우기

- 추천 글은 textarea 의 `placeholder` 속성으로만 넣는다. 80자를 넘으면 80자에서 자르고 `…` 를 붙인다.
- 입력 상자 안 오른쪽에 작은 표지 `Tab` 을 보인다.
- 입력창에는 `aria-description` 을 붙인다. `aria-live` 는 쓰지 않는다.
- Tab 이나 → 를 누르면 전체 글을 입력창에 채우고 커서를 끝에 둔다. 입력창이 비어 있고 명령 목록이 닫혀 있고 조합 중이 아니고 수식 키가 없을 때만 한다.
- 채우기는 pty 에 쓰지 않고 보내지도 않는다. Enter 는 사용자가 누른다.
- 사용 횟수 통계에는 `ghost` 종류를 더하지 않았다. 종류를 늘리려면 `lib.js` 의 통계 모양과 main·preload 의 허용 목록을 같이 고쳐야 한다.
- 개발용 화면 `MARU_APP_UI=readghost` 는 `readrail` 과 같고, 입력창에 추천 글 "다음 단계로 넘어가 줘" 와 `Tab` 표지가 보인다. 가짜 값이며 터미널을 읽지 않는다.

### 20.4 가정

- 가정: 턴이 끝난 뒤의 추천 글이 시작 안내와 같은 자리(`❯` + U+00A0 뒤)에 흐린 글자로 그려진다. 시험 세션에서 추천 글이 뜨지 않아 실측하지 못했다.
- 실측한 것은 시작 안내 `Try "…"` 와 대기열 안내 `Press up to edit queued messages` 가 그 자리에 흐리게 그려진다는 것이다.
- 터미널이 포커스를 잃었을 때 Claude Code 가 추천 글을 그리지 않을 수 있다. 이것도 확인하지 못했다.
